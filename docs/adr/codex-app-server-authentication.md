# Codex App Server authentication

RatelDesk #441 supports a customer-operated Linux runtime with private, operator-owned connections. The API hosts one pinned Codex CLI 0.170.0 process per active connection over stdio. Operators complete device sign-in in their own browser through the App Server's `account/login/start` request with `type: chatgptDeviceCode`. The runtime receives confirmation on its own network connection. The browser can run on another computer and needs only access to RatelDesk and ChatGPT. The operator or ChatGPT workspace administrator enables Codex device sign-in first. This route uses the official Codex client's managed sign-in. [App Server protocol](https://learn.chatgpt.com/docs/app-server#3b-log-in-with-chatgpt-device-code-flow) · [Headless sign-in](https://learn.chatgpt.com/docs/auth#login-on-headless-devices)

Commercial or shared hosted offering access requires an applicable OpenAI-approved registration and ChatGPT plan-use scope. Public source alone does not establish that permission. The local SIWC registration contract uses a loopback OAuth callback on the browser's computer. Remote OSS VM guidance requires local sign-in and protected credential transfer. A hosted deployment needs its own approved integration before exposing a browser or device ceremony. [SIWC registration](https://developers.openai.com/siwc/token-sharing-open-source/sign-in) · [Self-hosted VMs](https://developers.openai.com/siwc/token-sharing-open-source/self-hosted-vms) · [Commercial registration](https://developers.openai.com/siwc/request-client-id)

## Deployment and ownership

Mount the official verified runtime read-only on the API service. Provision a private, writable and encrypted local state volume. Installations opt in explicitly with `AiProviders:CodexAppServer:PrivateDeviceLogin`. Only the fixed executable and state directory are configurable at deployment. The package remains upstream-distributed, and the existing RatelDesk archive and image families retain their distribution contracts. [Pinned runtime and checksums](https://github.com/openai/codex/releases/tag/rust-v0.170.0)

A host identity and exclusive volume lock bind connections to one API host. A same-volume API restart can read the original thread history. A different volume or host cannot assume ownership. The connection owner and RatelDesk tenant are stored in PostgreSQL. Native tokens remain in the runtime's private credential store, separate from immutable profile revisions. The pinned runtime serializes refresh and atomically replaces its file. Reconnect starts a fresh credential generation. Disconnect stops local authority and calls the runtime's logout/revocation operation. When upstream confirmation is unavailable, remove local access and report the uncertainty. [Atomic credential storage](https://github.com/openai/codex/blob/rust-v0.170.0/codex-rs/login/src/auth/storage_file.rs) · [Native refresh and logout](https://github.com/openai/codex/blob/rust-v0.170.0/codex-rs/login/src/auth/manager.rs)

ChatGPT plan usage is scoped to the original connection, model, profile revision and RatelDesk operator. The harness uses the normal Codex ChatGPT route. The separate API-project path uses its own project credentials. Account metadata and the runtime picker establish setup state. The Codex catalog may use a runtime cache. Actual model access requires a completed turn. Read-only RatelDesk tools use the existing gateway with an expiring, resource-bound original-operator grant. The initial profile exposes read-only ticket MCP. Local workspace tools, skills, artifacts, delegated agents and write approvals stay unavailable until separately supported.

## Dispatch and evidence

The worker records a bound thread and reserves durable dispatch before calling `turn/start`. A JSON-RPC ID is a response correlation value. Recovery checks the original thread and user-message identity. A lost reply cannot trigger a second `turn/start`. Recovering saved history can continue after a browser disconnect. A worker or process failure can interrupt active work. The runtime reports cancellation and completion separately.

Linux x64 protocol checks used the published 0.170.0 archive and its published SHA-256. The test used a fresh isolated state directory and verified `initialize`, an official device challenge and its cancellation, and an empty `account/read` without authorizing an account. The session used the environment's standard HTTPS proxy and certificate bundle. An isolated protocol test with no reachable inference service also verified pinned thread creation, turn IDs and paged history after thread materialization. Owner sign-in, account-specific eligibility, a completed inference turn and a real MCP read remain live acceptance steps. [#441](https://github.com/BostonTechnologies/RatelDesk/issues/441)
