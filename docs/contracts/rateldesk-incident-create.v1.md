# RatelDesk reliable incident receiver v1

The authoritative contract is [rateldesk-incident-create.v1.json](rateldesk-incident-create.v1.json). The frozen semantic SHA-256 vectors are [rateldesk-incident-create.v1.fixtures.json](rateldesk-incident-create.v1.fixtures.json). Copy these exact files and this document into the producer repository before enabling delivery. Compare the file SHA-256 digests; neither a connector proposal nor successful authentication establishes receiver support.

This contract is owned by RatelDesk issue #116 and consumed by NetRatel epic #141 and connector PR #152. The separate M2M interoperability work is tracked in RatelDesk issue #89. V1 advertises only `api_bearer`. It adds no reciprocal pairing UX or OAuth service credentials.

## Routes and responses

All routes are relative to the configured API path prefix. Configure `StorageOptions:PublicApiBaseUrl` to the approved external API URL, including its prefix. Capabilities never derive credential destinations from Host or forwarded request headers. Missing/invalid configuration returns 503. Source identity comes from the approved registry, and receiver identity reuses the durable first-run `InstanceInitialization.InstanceId`.

| Operation | Method and route | Result |
| --- | --- | --- |
| Create | `POST /api/v1/incidents/` | 201 on commit; 200 on identical replay; immutable top-level IncidentDto plus integrationReceipt |
| Capabilities | `GET /api/v1/integrations/netratel/capabilities` | 200 with the required capability fields in the JSON contract |
| Reconcile | `GET /api/v1/integrations/netratel/incident-receipts/{key}` | 200 accepted create body and Location; 404 absent key in the authorized namespace |
| Validate target | `POST /api/v1/integrations/netratel/targets/validate` | 200 authorized normalized mapping; read-only |

Keyed create requires exactly one `Idempotency-Key` and one `X-NetRatel-Source-Instance`. The source is a lowercase nonempty GUID in D form. The key is case-sensitive ASCII URI-unreserved, 1–256 characters, matching `^[A-Za-z0-9._~-]{1,256}$`. Both headers are identifiers; neither grants authority. One missing header, empty/multiple values or invalid encoding returns 400 with `invalid-integration-headers`. A valid but unknown/foreign/unbound source returns 403 `source-not-authorized`. There is no fallback to ordinary create. Existing callers with neither header retain their ordinary DTO/result and creation behavior. A managed machine identity must always use both headers through the bounded authorization seam; no machine authentication mode is enabled in this implementation.

Use the key verbatim as one unreserved path segment. Do not percent-escape, case-fold or normalize it, including the rare `.`/`..` keys. Clients must preserve dot segments instead of allowing their URI builder to resolve them. New producers should use 64-character SHA-256 keys. Encoded path variants, invalid keys and receipt query strings return 400 `invalid-idempotency-key`; an invalid source header returns 400 `invalid-source-header`. A nonexistent key's 404 does not imply an in-flight create cannot still commit. Retry with the original key.

Creation, replay and lookup use `Cache-Control: no-store`. Successful responses include the captured resource Location. Replays also include `Idempotency-Replayed: true`. Later incident edits, renamed customers or changed customer email do not alter the stored accepted body. IntegrationReceipt has exactly the fixed string fields `contractVersion`, `receiverInstanceId`, `sourceNamespaceId`, `sourceInstanceId`, `key`, `fingerprint`, `outcome`, `incidentId`, `trackingId`, `organizationId`, `customerId`, `committedAtUtc` and `location`. `outcome` remains `committed`; the UTC timestamp uses RFC3339. Receipt incident/tracking/organization/customer identifiers agree with the top-level result.

The same authorized namespace/key with different submitted semantics returns 409 ProblemDetails, extension `code: idempotency-payload-conflict`. Authentication, live source membership, enabled organization/customer, operation permissions and approved mapping are checked before any receipt or conflict is exposed. A changed organization/customer outside the approved mapping returns 403 `target-not-authorized`, even when the key exists. Replay/lookup do not rerun mutable category/assignee selection rules. Fresh create and target validation do.

Target validation accepts required organizationId/customerId, optional assignedToId (omitted/null means null), and optional categoryIds (omitted/null means empty). Its 200 response has contractVersion, receiverInstanceId, sourceInstanceId, sourceNamespaceId, valid=true and mapping. The mapping preserves explicit null assignment and distinct canonical GUID D category IDs sorted ordinally. Malformed/oversized input returns 400 `invalid-target-request`; unauthorized mapping returns 403 `target-not-authorized`; invalid assignee or inactive/incompatible/foreign categories return 422 `invalid-incident-target` with bounded field errors and no entity details. It creates no ticket, job, customer or notification. Validation is an observation and does not replace checks at creation.

## Register and rotate a source

Use an authenticated interactive local/OIDC instance administrator. Integration credentials cannot manage this registry. Create the API-purpose credential with current incident permissions for an enabled owner and the intended organization using the existing credential management flow. Never place the opaque secret in source registration, audit logs or contract files.

1. Register with `POST /api/v1/integrations/netratel/sources/` and `{sourceInstanceId, organizationId, customerId, credentialId}`. IDs must refer to approved enabled local data; the customer must belong to the organization. The receiver returns 201 with its generated permanent sourceNamespaceId, approved mapping and revision=1. Unknown headers cannot self-register. A duplicate source instance returns 409 `source-already-registered`.
2. Inspect registrations with `GET /api/v1/integrations/netratel/sources/` (bounded to 256 results). Mapping and source identity are immutable. Each namespace has one approved organization/customer mapping.
3. For rotation, create a replacement API credential in the same organization. Bind it with `PUT /api/v1/integrations/netratel/sources/{sourceNamespaceId}/principal-bindings/{credentialId}` and `{expectedRevision, isEnabled:true}`. The source namespace remains unchanged, and the replacement can reconcile prior keys. A fresh unaffiliated credential cannot take over a source by copying its header.
4. Revoke the predecessor through existing credential management, or disable its binding with the same PUT and `isEnabled:false`. Disabling/revoking stops its access immediately on subsequent requests. The new source revision is returned; stale revisions return 409 `source-revision-conflict`.
5. Disable/enable the whole source with `PATCH /api/v1/integrations/netratel/sources/{sourceNamespaceId}` and `{expectedRevision, isEnabled}`. The namespace and accepted keys survive. No physical deletion or remapping operation exists.

Registration/grant changes commit source state, binding and audit together. Audit records contain actor, UTC time, operation, approved mapping, principal identifier, state and revision, without secret values. Every replica reads current persisted state. Credential validity, enabled owner, API purpose and the current owner's effective permission intersection remain mandatory. Registry membership cannot expand credential scope.

`IIncidentReceiverAuthorization` is the application boundary for future approved service principals. Its operation enum separates Create, ReadReceipt and ValidateTarget; binding keys distinguish principal kind from principal identity. A future implementation must map the three managed scopes in the JSON contract, require headers, enforce current service/source/mapping grants, and advertise OAuth only after real acceptance testing. The create route uses an explicit authenticated boundary plus per-request application authorization, so a later narrow machine grant need not inherit the human IncidentAccess role policy. Ordinary create still explicitly checks IncidentAccess. Other incident routes retain their existing policies. Token subject/client_id never becomes a requester or user FK.

## Semantic fingerprint and bounds

The receiver hashes a frozen typed projection using UTF-8 System.Text.Json Web defaults, compact JSON and the fixed property order in the JSON contract. The conformance vectors lock the exact serialized representation and hash. Property order in submitted JSON is irrelevant. Numeric priority uses the existing enum values 0–3. Strings are not NFC-folded or generally trimmed. Title/impact and ordered asset/attachment lists retain meaningful differences. Null/missing ordered lists equal empty lists. Category IDs are a distinct sorted set; empty GUIDs are omitted. CC values are trimmed, lowercased, distinct and sorted, independently of current customer email. Creation then omits the selected requester's email from delivery recipients.

Description uses the existing HTML sanitizer and plain-text converter before hashing and creation. Missing description defaults to empty; explicit null is invalid. Missing priority defaults to Low; null/string priority is invalid. Missing/null/whitespace assignment equals null. Missing/null impact equals null; an empty impact is distinct. Due dates normalize to UTC, with unspecified dates interpreted as UTC and an invariant roundtrip representation with seven fractional digits. The accepted requester's email always comes from the approved customer. DTO requesterEmail is ignored and excluded from the fingerprint.

Bodies are streamed into a bounded 131,072-byte buffer for keyed create, target validation and registry writes, including chunked bodies. Keyed input requires a nonblank title up to 256 characters, description up to 65,536, impact up to 4,096, mapping IDs up to 64, lists up to 128, asset/attachment strings up to 512 and CC strings up to 254. Violations fail before business effects. Ordinary no-header create retains its existing handling.

## Transaction, effects and retention

A real unique database index on (SourceNamespaceId, Key) reserves a receipt before calling CreateIncidentCommand. The incident, categories, SLA, notification/support delivery rows, immutable accepted JSON and ingress outbox effects commit in one database transaction. Existing `IIngressEffectContext` captures creation effects and confirmation, and `MailboxOutboxStore.FlushAsync` runs once before commit. Receipt GUIDs share the existing unrestricted outbox receipt namespace. The HTTP path binds captured email to the approved organization without entering background-only ingress routing authority.

A losing concurrent writer rolls back, disposes the failed context, and reads the winner in a clean scope. Provider execution strategies also create fresh operation scopes. SQLite competing-writer retries are bounded and cancellation-aware. Rollback leaves no accepted receipt or externally visible effect. Replay never calls the create command or captures effects again. One logical confirmation enqueue is guaranteed; existing outbox leases, retry and uncertain SMTP submission handling govern transport delivery. External SMTP is not exactly-once.

V1 retains full receipts indefinitely, advertises a 90-day minimum and disables eviction. Sender automatic retry must stop within 30 days of the original durable action creation time, with age persisted across restarts. Manual reconciliation can continue afterward. Future cleanup requires a durable tombstone or equivalent non-recreation barrier; removing a source/binding or rotating credentials must never make an accepted key new again.

## Validation and rollout

The receiver tests use the actual endpoint maps, real credential handler, current authorization service, application handlers and ingress decorators. Both provider migration chains are generated by normal EF tooling. Functional tests use file-backed SQLite and the repository's Testcontainers PostgreSQL harness without skips or mocks for persistence/authorization. They cover two independent API hosts and connections, response loss after commit, precommit fault/rollback, database reopen, separate real API process launches, source rotation, current authorization loss, immutable replay, validation, bounds and durable outbox claims. Golden vectors cover defaults/order equivalence and every consumed field's material change. Foreign scope changes are rejected by authorization before conflict disclosure.
