# 0.1.2-beta.5 — MCP campaign repairs

This release repairs three finding families from beta.4 source
`94c91712e880066ed3f4e87337bd2311adfc583a`:

- [#222](https://github.com/BostonTechnologies/RatelDesk/issues/222): MCP and CLI
  general notification summaries use the existing scoped summary endpoint.
  Total, unread and unread Error/Critical counts reflect the caller's whole
  authorized population. Error-only reads and actor-specific receipts retain
  their existing authorization.
- [#223](https://github.com/BostonTechnologies/RatelDesk/issues/223): all four MCP
  ticket-list adapters validate explicitly supplied pagination before business
  API calls. Page is 1–1,000,000 and page size is 1–100; mathematically integral
  JSON numbers are accepted. Omitted fields, search aliases, filtered totals
  and direct REST/CLI compatibility remain supported.
- [#224](https://github.com/BostonTechnologies/RatelDesk/issues/224): newly
  committed worklogs retain decimal effort and a stable worklog association in
  incident, request and change timelines, including internal notes. Refreshes
  agree with live events. The additive nullable `recordedHours` distinguishes
  measured zero from unavailable historical effort; `workLogId` identifies the
  associated canonical worklog. Legacy numeric `hours` remains compatible.

The migration adds nullable timeline columns on SQLite and PostgreSQL. Old
timeline rows have no direct worklog relationship or snapshot. Only exact,
unambiguous retained transactional timeline-outbox evidence can recover an effort
snapshot, leaving the unknown worklog link null; other historical effort remains
unavailable. There is no timestamp/text matching or guessed backfill, and
canonical WorkLogs, outbox history and ticket totals are preserved. Clients must
use `recordedHours` to determine whether effort is known. See the
[operation contract](../contracts/mcp-operation-contracts.md#notification-summaries-and-persisted-effort)
and [regression map](../implementation/0.1.2-beta.5-mcp-regressions.md).

Before upgrading, back up the database, bootstrap state, data-protection keys
and attachments together. Review the verified release manifest, pin all three
images to its immutable digests, and update Web/API/HTTP MCP and CLI/stdio from
the same release through the existing deployment owner. Retain databases,
migration histories, volumes, target-bound profiles, credentials, configured
expiry, saved mail controls and existing topology. Verify actual version/source
identities after the owner applies the upgrade. Publication performs no owner
deployment or restart and never moves `latest`.

The catalog retains 28 tools and all 154 operation names. HTTP configuration
`set`/`unset` remain unsupported by their transport contract. The independent
identifier-filter audit #196 remains separate. Archive formats, three image
families, both container architectures, setup entrypoints, notices, checksums,
manifest and attestations retain the existing distribution contract.

Development acceptance, verified public distribution and the next deployed
campaign have separate receipts. Delivery
[#221](https://github.com/BostonTechnologies/RatelDesk/issues/221) closes only
after anonymous public verification; campaign
[#219](https://github.com/BostonTechnologies/RatelDesk/issues/219) remains open
for version-specific positive outcomes and retained-state reconciliation.
