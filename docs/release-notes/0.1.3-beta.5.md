# 0.1.3-beta.5

This beta repairs RatelDesk's shared chat observation and composer defects in
[#351](https://github.com/BostonTechnologies/RatelDesk/issues/351) and retains
the exact-turn recovery safeguards in
[#308](https://github.com/BostonTechnologies/RatelDesk/issues/308).
Delivery against their full acceptance contract remains **PARTIAL**. See the
[evidence record](../implementation/0.1.3-beta.5-durable-chat.md).

## Changes

- A quiet model phase beyond the former five-minute cutoff keeps its healthy,
  owned native session and original active message. Later output and supported
  terminal events persist in the original conversation. Waiting/resumed notices
  are durable and repeated sweeps do not duplicate them.
- The shared ticket, organization Chat and Investigations UI shows elapsed
  time, last saved remote activity and waiting status. Connection health does
  not claim task completion. Received history survives refresh/navigation;
  fullscreen keeps the shared conversation mounted.
- Actual connection loss retains delivery uncertainty. Saved-session checks
  use bounded exponential backoff and stop after six unsuccessful attempts per
  process/conversation. The UI reports the next automatic check or offers an
  explicit manual check after the budget pauses. Neither path resends a
  message, business action or uncertain approval.
- Enter sends once and Alt+Enter inserts a newline at the selection across
  first-send, established, ticket, investigation and fullscreen composers,
  including a physical keyboard on a touch device. Proper Blazor input binding
  and the DOM submission value preserve the final typed characters. IME,
  repeat, empty/busy/disabled guards and the existing keyboard aliases remain.
- A live failed terminal event is described as an error rather than success.
  Refusal/error text already received remains in the transcript.

## Recovery limits and upgrade

No database migration or credential change is required. Existing SQLite and
PostgreSQL data and provider-profile/authorization boundaries remain intact;
native AI chat retains its PostgreSQL requirement.

After missed output or an API restart, inspected NetClaw history supplies no
durable exact-message terminal/approval replay contract. RatelDesk therefore
retains uncertainty, even if history contains assistant text, Ready or a larger
turn count. Abandonment, uncertain approval and retired-owner late-output fences
remain. A 45-minute deployed native run and restart acceptance are still required
before #351/#308 can be closed. Fixture clocks and rendered browser tests do not
establish that acceptance.

The separate [NetClaw #2791](https://github.com/netclaw-dev/netclaw/issues/2791)
provider-stream work is outside this RatelDesk beta. This beta does not establish
the cause of the reported approximately 643-second provider phase and does not
publish or change upstream NetClaw.

## Owner acceptance after deployment

1. In a disposable conversation on each shared consumer, run harmless work for
   at least 45 real minutes. Keep its original message/session/profile and
   confirm one final answer and terminal outcome, including a refusal/error.
2. Refresh, navigate and toggle fullscreen during the quiet phase. Verify
   waiting status and ordered saved history without a second send/action.
3. Interrupt the native connection, then restart the API separately. Inspect
   exact supported replay evidence and the remaining unknown outcome; do not
   treat admission or connectivity as completion.
4. Exercise pending and uncertain approvals using their original call IDs and
   options, then abandon one unresolved turn and verify late output is fenced.
5. Type quickly, paste multiline text, replace a selection with Alt+Enter and
   submit with Enter in every composer. Confirm exact text and one admission.

## Distribution

Root `Directory.Build.props` owns `0.1.3-beta.5`. The existing hosted workflow
must verify seven archives, checksums, the release manifest, three image families
(`rateldesk-api`, `rateldesk-web`, `rateldesk-mcp-http`) and amd64/arm64
SBOM/provenance before public completion. Use exact version tags or immutable
digests. Beta publication preserves stable `latest`. Publication and deployment
receipts are distinct from source verification.
