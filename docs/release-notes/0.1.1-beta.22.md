# 0.1.1-beta.22 — single-origin routing and explicit client setup

This beta implements single-origin routing and explicit client/host setup.
Distribution below describes the hosted workflow contract. Publication and
verification evidence are recorded with the GitHub release; these source notes
do not establish public-download verification or owner acceptance.

Scope: [documentation #154](https://github.com/BostonTechnologies/RatelDesk/issues/154),
[gateway #155](https://github.com/BostonTechnologies/RatelDesk/issues/155),
[configuration #156](https://github.com/BostonTechnologies/RatelDesk/issues/156),
[browser pairing #157](https://github.com/BostonTechnologies/RatelDesk/issues/157),
[Termina setup #158](https://github.com/BostonTechnologies/RatelDesk/issues/158),
[HTTP hosting #159](https://github.com/BostonTechnologies/RatelDesk/issues/159), and
[navigation #160](https://github.com/BostonTechnologies/RatelDesk/issues/160).

## Changes

- Documentation now has a categorized [index](../README.md), preserved
  [path migration map](../implementation/documentation-migration.md), and
  canonical repository placement/configuration/release instructions.
- [Web gateway](../deployment/web-gateway.md) resolves one API destination and
  exposes selected HTTP MCP through the public Web origin. Explicit custom
  topology/ReverseProxy overrides, existing API/OpenAPI/assets, optional manual
  MCP routes and supported file reload remain available. Selected outages return
  proxy failures; absent MCP paths return JSON rather than Blazor HTML.
- [Shared configuration](../integrations/cli-stdio.md) supports typed validation,
  isolated CLI/MCP surfaces, dedicated environment-only MCP settings, secret-file
  references, redacted provenance, explicit profiles and protected persistence.
  Legacy CLI variables/files and isolated MCP JSON remain supported.
- [Browser-approved pairing](../integrations/browser-pairing.md) issues ordinary
  revocable account credentials for one approved organization, purpose/resource,
  permissions and expiry. Durable private staging precedes acknowledgement;
  the working profile activates only after confirmed acknowledgement. Explicit
  setup re-entry recovers interrupted delivery without replacing an older
  working profile prematurely.
- Explicit Termina [setup commands](../integrations/cli-stdio.md) connect CLI,
  stdio MCP and HTTP clients or export host settings. Setup supports keyboard
  navigation, masked/private secrets, managed fields, cancellation and bounded
  read-only checks. Normal serving never opens a wizard; stdio stdout stays
  JSON-RPC only. External OAuth client setup saves reviewed non-secret metadata,
  leaving sign-in/tokens and actual acceptance to the external client.
- [HTTP MCP deployment](../mcp-http/deployment.md) provides coordinated Web/API/MCP
  environment recipes and standalone container tooling, protected persisted
  export mounts, explicit apply/recreate steps and gateway versus Authentik
  [mode/configuration guidance](../mcp-http/configuration.md). Gateway stores no
  downstream deployment credential or shared delegation key.
- Navigation uses compact rows, aligned icons, restrained active accents and
  separated account access to Integration credentials. Most-specific leaf
  matching, authorized menu destinations, tenant scope, branding and mobile
  controls remain part of the existing application. See the
  [route map and verification evidence](../implementation/single-origin-navigation.md).

## Upgrade and migration

1. Pin the existing release/digests and back up database, bootstrap state,
   data-protection keys and attachments together. Preserve existing account,
   instance and integration identities. SQLite and PostgreSQL remain supported;
   existing PostgreSQL native-chat requirements are unchanged.
2. Review the canonical guides and explicit custom addresses/ReverseProxy
   overrides before changing configuration. `ApiBaseUrl` now owns Web clients
   and generated API routing; deliberate advanced divergence remains explicit.
   Configure trusted public HTTPS identity separately from private backend DNS.
3. Select HTTP MCP deliberately. The base stack leaves it unselected. An MCP
   overlay must configure both Web's Enabled/Destination and the HTTP host.
   API browser-pairing origin must align with the intended public instance.
   Retain file-based deployments or adopt dedicated MCP environment settings;
   never import ambient CLI credentials into MCP.
4. Review exported settings privately, preserve API volumes/keys and explicitly
   recreate the intended services. Setup cannot edit a parent shell, another
   running container's environment or immutable secrets. Use the actual Docker
   host path for exported mounts. Serving remains UID 10001; one-shot setup can
   use the operator UID/GID for writable output. Protect Unix files/directories
   and Windows ACLs according to the shared configuration contract.
5. Use API-purpose credentials for CLI/stdio and an exact public-resource-bound
   MCP-purpose credential for gateway HTTP clients. Browser approval uses
   existing local/MFA/linked-OIDC sign-in and current account grants. Manual
   existing credentials and explicit external Authentik remain available.
   Interrupted browser delivery resumes through explicit setup; normal runtime
   ignores private pending sidecars and retains the working profile.
6. Verify configuration, routing, authentication, MCP initialize and one
   permitted read-only upstream tool result separately. Keep external OAuth
   client checks marked unverified until its own sign-in and MCP connection
   complete. After verifying a replacement client credential, revoke the retired
   credential in account management. External ingress/downstream identities
   rotate separately; gateway has no shared/downstream secret to rotate.

Existing NetClaw, NetRatel and mailbox configuration is preserved. This beta's
client credential pairing does not replace those separate system connections.
No production deployment is part of implementation/release preparation.

## Distribution and acceptance

The hosted release workflow retains three images (`rateldesk-api`,
`rateldesk-web`, `rateldesk-mcp-http`) for amd64/arm64 with image SBOM/provenance,
and self-contained CLI/stdio archives for Linux x64/arm64 and Windows x64.
Existing archives include explicit setup, canonical guides and license notices;
deployment archives keep flat Compose paths. Checksums, source revision,
release manifest/detached checksum and immutable image digests must be verified.
Linux native archives require glibc.

Successful staging creates a draft release. Publication and anonymous downloads
and image pulls must be verified before declaring distribution complete. A beta
does not move `latest`. See [release engineering](../releases/README.md).

Owner walkthroughs for the real HTTPS ingress, browser approval, SSH/terminal
setup, container recreation, streaming/cancellation and credential rotation
remain separate acceptance. Record actual results and deployed identities;
local tests, a reachable port or a release page alone do not establish them.
