# 0.1.2-beta.6 — durable delivery and MCP acceptance repairs

Beta.6 repairs delivery history and callback integrity found while preparing the
next MCP campaign. It also makes HTTP execution authority observable, reduces
notification-summary database work and supplies an executable individual
acceptance register. The baseline is beta.5 source
`07ec0a48f4b24656f56eac265e38ac24c687ffa4`.

## Changes

- [#227](https://github.com/BostonTechnologies/RatelDesk/issues/227): a public
  worklog's queued email keeps its canonical delivery event pending. Both direct
  and transactional ingress paths preserve the exact worklog, ticket and durable
  effect relationship. Only dispatch evidence can mark delivery. Missing or
  disabled senders, definite failure, partial delivery and uncertain outcomes
  retain their distinct histories. Retries reuse the same owner, and internal
  notes cannot become outbound mail. A failure after durable queue acceptance
  does not overwrite dispatch-owned history with an invented send failure.
  The Graph processing path reports durable queue acceptance as queued.
- [#228](https://github.com/BostonTechnologies/RatelDesk/issues/228): the new
  read-only `helpdesk_auth.access` operation reads the business API's actual
  execution principal and current access profile. HTTP discovery describes
  configured ingress and downstream identities separately. The ordinary gateway
  credential retains its tenant scope. External Authentik uses the separately
  configured downstream bearer and its actual provider-issued claims; inbound
  MCP tokens are not forwarded to a different resource. Discovery metadata
  cannot grant missing authority. Exact AI status/report/log operations retain
  their separate AuthentikAiAgent requirement.
- [#231](https://github.com/BostonTechnologies/RatelDesk/issues/231): the request
  form builder uses the saved automation connection's organization and peer
  tenant. It preserves the selected connection on each binding, verifies its
  current settings and scopes catalog reads, target creation and input sync to
  that connection. A single eligible connection can be selected automatically;
  multiple connections require a choice, and an unavailable stored connection
  cannot fall back to another peer. The API independently checks the target
  tenant and job before saving. Drift and import use each binding's saved
  connection. The legacy organization tenant field is not changed or used as a
  substitute for the active mapping.
- [#234](https://github.com/BostonTechnologies/RatelDesk/issues/234): AI callback
  event IDs are bound to the same invocation, organization, ticket, correlation
  and stored report fields. Matching callbacks remain idempotent without
  rewriting timestamps or run references; conflicting replays
  and cross-invocation collisions fail. A late progress callback cannot regress a
  Completed, Failed or Cancelled invocation. Dispatch failure also preserves a
  terminal callback that arrived while the webhook request was in flight.
  The relational status transition
  and event persistence share a transaction, including concurrent duplicates.
  These are source-review findings; they do not add reproduced beta.5 failures.
- [#233](https://github.com/BostonTechnologies/RatelDesk/issues/233): total,
  unread and unread Error/Critical notification counters now aggregate the same
  authorized population in one database statement. Tenant, module, customer and
  actor-specific receipt rules are preserved, including an empty population.
  A synthetic HTTP workload measures database command counts and latency on
  SQLite and PostgreSQL. It does not invent a retrospective service-level target;
  the deployed campaign still needs its prospectively agreed workload and budget.
- [#232](https://github.com/BostonTechnologies/RatelDesk/issues/232): an
  [individual closure register](../implementation/0.1.2-beta.6-acceptance/README.md)
  preserves all 59 historical blockers, the P1 defect, S1–S5, the original eleven
  finding families, eight beta.4 regressions, the latency observation and the
  new access operation. Its 86 obligations begin OPEN with production readiness
  NO. Structural CI validates the template; the acceptance mode requires actual
  private evidence and rejects missing, stale or inconsistent receipts.

The current catalog has **28 tools and 155 operations**. `helpdesk_auth.access`
is the sole operation addition; historical 154-operation catalog evidence remains
versioned. The live campaign must rediscover the exact wire schema, reconcile the
current catalog and rerun every historical case. HTTP configuration `set` and
`unset` retain their existing transport restriction. See the
[operation contracts](../contracts/mcp-operation-contracts.md) and
[HTTP configuration guide](../mcp-http/configuration.md).

## Regression and acceptance evidence

The existing five normal PR/main gates remain in place. The provider gate now
also requires actual SQLite and PostgreSQL execution of
`WorklogMailDeliveryTests`, `AiInvestigationMcpHttpTests`,
`AiInvestigationDispatchRaceTests`, `OrchestrationConnectionSelectionHttpTests`
and `NotificationSummaryPerformanceTests`, with no absent or skipped selected cases.
The worklog suite captures isolated SMTP outcomes and checks task failure,
canonical ownership, replay, cancellation and retry. HTTP identity regressions
use a synthetic signed provider and the production API authentication path.
They do not establish acceptance against an external provider deployment.

Source tests and release distribution do not supply the missing production
prerequisites. The original immutable campaign corpus and beta.5 reproduction
files are not part of the public template. Each of the 59 operations still
requires its own acknowledged owners, positive execution, isolation readback
and evidence. Eligible support self-assignment, a linked customer with owned
requests, actual automated retry, the exact AI reporting identity, expired AI
credentials and bounded diagnostic-log authorization remain explicit acceptance work.

The complete fresh campaign, original case reconciliation, 15-minute bounded
soak, restoration and independent review remain under
[#219](https://github.com/BostonTechnologies/RatelDesk/issues/219). Passing source
tests or publishing this prerelease cannot change that issue's readiness verdict.

## Upgrade and distribution

Beta.6 introduces no database migration. Back up the database, bootstrap state,
data-protection keys and attachments together before an owner-managed upgrade.
Select matching Web, API, HTTP MCP and CLI/stdio artifacts from the verified
manifest and pin container deployments to its immutable digests. Preserve
databases, migration histories, volumes, target-bound profiles, credentials,
configured expiry, saved sender/worker controls and topology. Existing history
is not inferred from matching text or timestamps.

The release retains seven archives, three image families with Linux amd64/arm64,
native Linux x64/ARM64 and Windows x64 execution checks, checksums, manifest,
notices and SBOM/provenance. Delivery
[#226](https://github.com/BostonTechnologies/RatelDesk/issues/226) records the
reviewed merge, exact-source CI and anonymous public verification. Publication
performs no owner deployment and does not move `latest`.
