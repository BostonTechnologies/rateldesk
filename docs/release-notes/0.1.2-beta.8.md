# 0.1.2-beta.8 — delegated owner operations over HTTP MCP

## Owner authority

An enabled instance administrator can explicitly authorize an
`owner-administration` MCP credential. Consent identifies access across all
organizations. The API persists this as a separate grant kind, binds it to the
selected MCP resource and expiry, and rechecks the source credential and the
owner's current enabled administrator status on each request. An ordinary
credential remains limited to its approved organization and permissions.

An owner grant can administer organizations even when its original default
organization has been disabled. With no enabled organizations, global recovery
operations remain available without silently selecting another organization.
Revocation, expiry, account disablement and loss of administrator authority
invalidate subsequent execution, including cached execution tokens. Existing
credentials require deliberate new consent to receive owner authority.

The same explicit owner identity can use bounded operational log searches and
report on a real, dispatched AI investigation. Invocation, ticket and correlation
binding, duplicate-event handling and terminal-state rules still apply. Local
account deployments do not require an unrelated external identity provider to
perform those owner operations. External AI authentication remains separately
validated.

## Typed operator capabilities

The beta.8 export contains 37 tools and 389 operations: 234 additions with all
155 beta.7 operations retained. These are advertised capabilities; their fresh
deployed acceptance is measured by the separate beta.8 campaign.

The catalog adds named, schema-validated operations for self-service form and
automation creation, binding maintenance and input synchronization; task
approvals and workflow diagnostics; attachments; mail delivery and recovery;
mailbox, sender, template and rule administration; support groups and routing;
SLA policies and calendars; datasets and ingestion; paired system connections;
and tenant/account administration. The final UI-to-MCP comparison also adds
automation rules, assets, instance and tenant branding, background-worker
settings, ticket lookup and current-assignee recovery, scoped dashboards and
notification views, NetClaw setup/testing, owned credential metadata and incident
source management.

AI operations include configuration, eligible providers, explicit dispatch,
investigation worklogs, and the native conversation lifecycle. Opening a new
conversation requires confirmation; ordinary conversation reads require its
existing identifier. Native chat retains its actual PostgreSQL and configured
provider requirements. Reconciliation, stop-waiting and abandonment preserve the
distinction between a failed action and an uncertain outbound effect.

Every adapter selects a compiled HTTP method and canonical API route. Schema
validation, confirmation previews and the API's actual permissions apply to
each operation. Callers cannot supply arbitrary URLs or HTTP methods. Required
fields, numeric bounds, enums and date/time formats are executable contracts.
Integral JSON numbers such as `1.0` are normalized for typed integer fields.

Authenticated request-task and change approvals require the stored designated
approver's identity and organization access. An owner cannot impersonate another
approver. Shared decision fences preserve one committed transition across signed
links, authenticated actions and concurrent lifecycle work, with audit and
notification intent stored transactionally. Account
activation, dataset ingestion and system pairing can return a newly issued
one-time credential only in their explicitly confirmed lifecycle result.
Ordinary reads, previews and diagnostic evidence redact secret values.

HTTP MCP intentionally cannot edit its host's local connection files through
`helpdesk_config.set` or `helpdesk_config.unset`. Platform administration uses
the typed API-backed settings operations. External self-provisioning belongs to
the configured external identity mode; Local deployments use the new local
account lifecycle operations.

## Correctness and hardening

- Direct email submission distinguishes durable queue acceptance, provider
  acceptance and an unconfirmed result. A transport success never claims
  recipient delivery. Failed or partial outcomes require delivery evidence
  before retrying.
- Authenticated dataset writes use the dataset's organization and source
  authority while preserving the separate ingestion-key API. All writers share
  a database fence, bounded case-insensitively unique keys and atomic batches.
  Legacy key collisions require an explicit reviewed full replacement; a failed
  batch cannot be accidentally persisted by a later background status update.
- AI dispatch idempotency is bound to its organization, ticket, configuration,
  acting operator and instruction. Concurrent first submissions create one
  invocation, and a failed queue commit produces no outbound request.
- Form schema updates preserve an omitted audience. The form task summary and
  timeline count reflect the visible saved content, including system events.
- SignalR and PKCS use the vendor-patched 10.0.13 packages. The isolated CAPTCHA
  bitmap uses bounded PNG encoding without the general ImageSharp dependency.
  Its public response contains the image and challenge identifier, not the
  correct answer; validation remains server-side and single-use.
- HTTP-MCP responses are non-cacheable, including the explicitly confirmed
  one-time activation, ingestion-key and pairing results.

The beta.7 Auto Start, binding-save, strict list-schema and retry repairs remain
required regressions. Genuine terminal-attempt retry also needs the companion
NetRatel repair; the preceding campaign used NetRatel `v0.1.1-beta.29`.

## Acceptance and distribution

The required provider lane covers real HTTP owner delegation and pairing on
SQLite and PostgreSQL, owner/external AI callback execution, and ordinary
credential isolation. Its receipt checker rejects missing, skipped or failed
required cases. Catalog tests validate the actual canonical API route and DTO
contracts alongside executable discovery.

The [beta.8 campaign contract](../implementation/0.1.2-beta.8-campaign.md) requires
fresh deployed evidence for every applicable advertised operation, the critical
business scenarios and a bounded soak. Historical beta.6 and beta.7 evidence is
retained as history; source tests and publication do not substitute for the
owner's beta.8 deployment campaign. The live acceptance issue remains
[#219](https://github.com/BostonTechnologies/RatelDesk/issues/219).

Release engineering produces the existing three multi-platform images, six
self-contained CLI/stdio archives, deployment archive, checksums and manifest.
The exact prerelease does not move `latest`. See the published release and its
manifest for the immutable source and image digests.
