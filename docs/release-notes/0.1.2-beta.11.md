# 0.1.2-beta.11

Completes the beta.10 transport and inbound-rule lifecycle repairs and supplies
an executable, current-release laptop acceptance gate.

## Product changes

- HTTP MCP and the public Web gateway enforce the same decoded JSON request
  body limit for Content-Length and chunked uploads on `/mcp` and `/mcp/`.
  The default remains 30,000,000 bytes. Oversized requests receive a structured
  HTTP 413; framing has a separate finite budget. Tighter configured limits
  remain effective. Buffered requests have bounded memory, disk and concurrency
  use. Existing duplicate-argument validation remains in place (#266).
- Administrator inbound email rules support selected-rule deletion through
  `DELETE /api/v1/inbound-email-rules/{ruleId}` and the confirmed MCP operation
  `helpdesk_email_settings.delete_rule`. Processing history remains available,
  and existing owner/ordinary authorization boundaries apply (#267).
- The catalog contains 37 tools and 390 operations at revision
  `2026-10-25.beta11-contracts-v25`. All 389 previous operation identities are
  retained; `delete_rule` is the single addition.

## Campaign execution

The [laptop guide](../mcp-http/beta11-laptop-campaign.md) and
[current validator](../../tools/ci/validate-beta11-campaign.py) bind evidence to
the published beta.11 source, manifest and catalog. They retain the 103 domain
cases, 86 historical obligations, nine cleanup assertions and post-functional
soak. Historical beta.8 through beta.10 receipts remain unchanged.

New tooling acquires selectors from fresh independently verified fixtures,
tests the real HTTP framing boundary, records prerequisites before mutation
lanes, and reconciles evidence as each lane completes. Direct mail and approval
replay require exact durable effect accounting. Only the documented volatile
SLA countdown fields can receive a bounded parity tolerance.

## Paired provider and deployment

The accompanying NetRatel history repair is tracked by NetRatel issue #410.
Ordinary definition retirement must retain terminal run evidence for the paired
cleanup gate. Use the exact companion release recorded in the published handoff
and a fresh owned run to prove that behavior.

The owner deploys the published artifacts; the laptop campaign then verifies
identity and executes acceptance. A ready global mail sender, isolated delivery
recipient, current bounded NetRatel authority, online execution target and real
AI/provider fixtures are explicit preflight requirements. The full live verdict
remains tracked by [#219](https://github.com/BostonTechnologies/RatelDesk/issues/219).

Publication follows the existing hosted release workflow, immutable native and
deployment archives, checksums, manifest and three multi-architecture image
families. Delivery is tracked by
[#268](https://github.com/BostonTechnologies/RatelDesk/issues/268).
