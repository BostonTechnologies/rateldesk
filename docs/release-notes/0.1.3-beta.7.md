# 0.1.3-beta.7 — OIDC administration and authoring editors

An explicitly authorized OIDC instance administrator could sign in and see
`HelpdeskAdmin`, yet Integration returned HTTP 403 because no application
credential owner had been persisted. Successful administrator provisioning now
creates one passwordless owner bound to the validated issuer and subject in the
existing Identity login store. Credential and system-connection management can
resolve that owner without creating a customer-contact association.

Account disablement remains authoritative, and provisioning never reenables an
account. Provider claims and explicit API mappings still determine current
administrator access. Resolving a fresh token without that authority updates
the persisted administrator projection used by owned credentials. Matching
email addresses do not associate accounts. Existing local and customer-linked
OIDC ownership is unchanged. There is no schema migration. Local sessions retain their existing owner;
integration, MCP, gateway, service, machine and AI-agent sessions cannot use
this provisioning path to create an OIDC owner.

Configured provider-group names containing `:` are now resolved as complete
mapping keys. Previously dictionary binding interpreted the separators as
configuration nesting and silently omitted those groups, including the shipped
`rateldesk:role:admin` mapping. Both `groups` and `roles` claims are covered.

## Grouped custom-role editor

Create, edit and clone custom roles in a focused, responsive dialog. Search
permissions by name, key or family; select a complete family or individual
permissions, select the displayed search results, or clear the selection.
Family controls show complete and partial selection states. Search preserves
selections outside the current results, and Save/Cancel remain in the footer.

The reusable grouped selector only displays the caller's eligible permissions.
Organization ownership, protected built-ins, dependency checks and the API's
tenant-administrator delegation ceiling remain authoritative. Editing keeps the
role's organization fixed. Failed saves retain the draft; Cancel confirms
discarding changes. A role containing grants above the current editor's
authority requires instance-administrator review rather than silently losing
those saved grants.

## Request-service authoring

The request-form editor now starts with **Form setup**, followed by **Form
fields** and **Workflow**. Setup separates form details from publication and
organization settings. Task details and automation use bounded, grouped forms
with compact refresh actions, readable spacing and responsive cards. The
existing workflow navigator, ordering, dependencies, script browsing, preview,
validation focus and save/retry behavior are preserved. Switching tabs keeps
the same unsaved draft.

## Validation and operator checks

Signed-token API regressions cover repeated provisioning, credential listing,
system-connection listing, passwordless ownership, disabled accounts, admin-claim
removal, same-email/different-subject denial and invalid issuer/audience/signature
or expired tokens. Related ownership and effective-access regressions are part
of focused validation. Hosted PR/main checks and release distribution still
need their own successful receipts.

After deploying, sign out and in through the configured provider as an intended
instance administrator. Open **Administration → Integration** and check both
credentials and system connections. Verify a scoped user cannot manage instance
connections; verify account disablement and a fresh non-admin token deny access.
Then use the ordinary system pairing workflow for the intended peer. A successful
build or release does not establish this deployed acceptance.

Provider tokens can retain old claims until expiry or refresh. Disable the
application account for immediate local denial. See [OIDC account ownership](../security/rbac.md#oidc-account-ownership).

For UI acceptance, create, edit and clone a disposable custom role; inspect
family selection, search-hidden selections, permission dependencies, rejected
saves and explicit cancellation. Check narrow layouts and keyboard operation.
Open a request form, verify the setup-first tab order, edit across tabs and
confirm that workflow identities/dependencies and field values survive Save
and reload. Visual fixture checks use synthetic records; operator acceptance
on a deployed instance remains separate.
