# 0.1.2-beta.1 — self-service MCP setup

This candidate extends the single-origin/Termina foundation released in
0.1.1-beta.22 and preserves the stable 0.1.1 workspace and operational controls.
The owning delivery tracker is [#179](https://github.com/BostonTechnologies/RatelDesk/issues/179),
with [release acceptance #188](https://github.com/BostonTechnologies/RatelDesk/issues/188).
Source notes describe the candidate; completed CI, functional acceptance and
public distribution require their separately recorded exact-source evidence.

## Setup and access changes

- [URL-first setup](../mcp-http/setup.md) chooses the executable's client
  transport automatically, preserves explicit options and managed values, and
  keeps durable client storage separate from HTTP host output.
- The deployment-host launcher adopts the actual ordered Compose sources and
  ownership context, checks effective configuration before approval, exports a
  complete external-manager deployment document and resumes after recreation.
  Saved, apply-pending, verify-pending and verified states remain distinct.
- Host approval authorizes the reviewed non-secret deployment proposal. Its
  separate temporary verifier is explicitly approved, narrowly restricted to
  status checks, short-lived and cleaned up with truthful recovery status.
  Verification includes observed runtime, the real MCP catalog and successful
  API-backed `helpdesk_auth/status`, not only HTTP success or initialization.
- Account access uses compact host/client review surfaces and a shared grouped
  ordinary permission selector. Ordinary credentials retain exactly one enabled
  organization, exact selected permissions and the existing 30-day default and
  90-day maximum lifetime. Credential revoke/delete and selected inactive
  cleanup remain owner-scoped and durable.
- System connections retain authorized organization context and resumable
  incomplete setup. NetRatel service pairing, NetClaw device pairing and personal
  CLI/MCP credentials remain separate identities.

The reference sequence is NetRatel #242–#249 / PR #251, diagnostic fix PR #252,
beta.18 PR #258, existing-stack PR #260 and the relevant MCP/integration changes
from beta.20 PR #273. RatelDesk retains its own API routes, permissions,
one-organization grants, instance labels and supported private API destinations.
NetRatel's persistent gateway service secret/shared signing key, Jobs, updater
and unrelated navigation changes are outside this release.

## Upgrade and retest

Back up the existing database, API data-protection keys, attachments and protected
deployment configuration. Retain instance labels, private API targets, ingress,
volumes, external Authentik settings and integration identities. SQLite and
PostgreSQL remain supported; PostgreSQL-only native chat is unchanged.

Use the verified deployment archive's `./setup-http-mcp.sh` on the deployment
host. Apply only through the declared deployment owner. Recreate the selected
services, then run a new `./setup-http-mcp.sh --verify` invocation. A changed
source requires renewed review. Connect each consumer/organization separately
and check temporary-verifier cleanup and credential management. See the
[quickstart](../mcp-http/setup.md) and [complete deployment reference](../mcp-http/deployment.md).

## Distribution and acceptance

The existing hosted release flow retains Web, API and HTTP MCP images for
amd64/arm64 with SBOM/provenance, six self-contained CLI/stdio archives for Linux
x64/arm64 and Windows x64, and one deployment archive. The deployment archive
includes the executable launcher and adjacent Python helper at its root;
canonical guides and third-party notices/licenses remain bundled. Linux native
archives require glibc. Host launcher prerequisites are Docker with Compose and
Python 3; it performs no package installation.

Verify all seven archives, `SHA256SUMS`, the release manifest and detached
manifest checksum, exact source/tag/version, immutable image digests/platforms
and anonymous downloads/pulls. A staged draft or green source build is separate
from public distribution verification. Beta publication does not advance
`latest` or authorize an owner production deployment. Owner deployment acceptance
remains a separate retest; see [release engineering](../releases/README.md).
