# 0.1.2-beta.20 candidate

This candidate repairs the handling of a paired automation provider's `unknown`
execution outcome. Previously the callback was rejected as an invalid status,
leaving the task showing processing after the provider had reported uncertainty.
It also repairs an ordering window where a callback preceding the ingest
acknowledgement was permanently rejected. A callback matching the authenticated
current mapped attempt now receives a temporary HTTP 503 until the normal ingest
response establishes the remote identity. No callback can create that identity;
stale, foreign or conflicting attempts remain denied.

An authenticated callback matching the current mapping and recorded request/run
now holds the task and parent request for reconciliation. Provider IDs, attempt
history and previous results are preserved. Automatic, single-task and bulk
retries are held, and both task views show **Reconciliation required**. A later
known result for the same execution can resolve the hold; duplicate or stale
callbacks cannot regress a known outcome. Existing authorization and correlation
boundaries remain required.

Regression coverage exercises SQLite and PostgreSQL through authenticated HTTP
callbacks, restart, retry entry points, result preservation and late delivery.
It also covers early callbacks before acknowledgement, current-attempt and mapping
isolation, conflicting/partial identities, restart and subsequent acknowledgement.
The repair does not establish why a provider execution became uncertain or prove
that an unacknowledged process did not run. See the [operator guidance](../integrations/netratel-orchestrator.md).

Publication follows normal reviewed PR/main checks and the hosted immutable
release workflow. Published beta.19 assets and evidence remain unchanged.
Source tests and publication do not establish fresh deployed acceptance. The
complete operation and scenario coverage, real provider checks, final soak,
cleanup and strict evidence validation remain required under
[#219](https://github.com/BostonTechnologies/RatelDesk/issues/219).
